# 音符碰撞：代码结构、行数与精简建议

分析日期：2026-11-16。分析对象为当前 `code` 工作区，应用版本 0.2.0。

本次梳理结构并提出方案，没有实施功能删减或重构。工作区原有的 `AudioService.cpp` 注释修改保留。

## 1. 先看结论

真正参与应用运行的自有 C++ 源码在 `src`，共 **25 个文件（12 个 .cpp、13 个 .h）、4,386 行**。扣除空行和整行 `//` 注释后为 **4,074 行**。这不是 4,386 行游戏判定算法：判定、计分和游戏时钟合计只有 **541 行**。

代码难读的主要原因是两个大类承担太多工作：`MainWindow.cpp` 1,011 行、`LanSessionService.cpp` 901 行；再加成绩和谱面两个存储实现，四个 .cpp 共 2,686 行，占整个 `src` 的 61.2%。

建议先保留目前功能，通过缩短大函数、去除无效分支、复用明确重复的处理，让代码更容易解释。是否取消联机属于下一层的需求选择；不能把删掉联机与普通重构混为一谈。

## 7. 运行流程：先读这一条主线

```text
main.cpp
  └─ MainWindow：准备歌曲和设置，显示页面，接收信号
       ├─ SongRepository：读 index.json 和谱面 → Chart
       ├─ AudioService：加载 WAV → 起播通知
       ├─ SongClock：从真正起播时刻开始计算歌曲时间
       ├─ GameWidget：D/F/J/K 按下/松开 → MainWindow
       ├─ GameEngine：输入 + 歌曲时间 → 音符判定和 PlayStats
       │    └─ ScoreService：统计 → 分数、准确率、评级
       ├─ GameWidget：读取引擎状态，按歌曲时间绘制
       ├─ RecordRepository：正常完赛后保存，查询排行榜
       └─ LanSessionService：双人时增加准备、计划开局、比分和结果确认
            ├─ ProtocolCodec：TCP 数据拆包/组包
            └─ ClockSynchronizer：两端时钟映射
```

单人需要等音符全部结算且媒体自然结束；联机还要等双方结果确认。单看 `GameEngine::finished()` 不能认为此时一定可以入榜。

建议阅读顺序：`Models.h` → `ScoreService.cpp` → `GameEngine.cpp` → `GameWidget.cpp` → `MainWindow.cpp` 的 `startSolo/tick/finishIfReady` → 存储 → 网络。第一次阅读可以跳过全部构建产物、生成歌曲脚本和网络异常测试。

## 8. 精简方向与优先级

### 第一优先：保留功能，先降低阅读负担

**A. 拆短 MainWindow 的长函数，先不增加一堆新类。**

`buildUi()` 位于 172—494 行，约 323 行，混合了八个页面、样式和按钮事件。先在同一类内提取 `buildHomePage/buildPreparePage/buildLobbyPage/buildGamePage/buildResultPage/buildRankingPage/buildSettingsPage/buildHelpPage`，并将信号连接按单人、媒体、网络分组。每个函数只处理一个页面或一类事件。

效果：单次阅读范围明显缩小；总行数可能略增。这是降低理解成本最直接的一步。随后可按需要把样式移入一个 .qss 文件，或用 Qt Designer 的 .ui 文件减少手写布局；后者会增加资源和生成层，不能把减少的 C++ 行数算作整个项目同等减少。

**B. 简化已有的重复逻辑。**

- `ScoreService.cpp:21`：Perfect/Great/Good 分支重复增加 Combo 和权重，可让分支只更新各自计数，再集中更新权重与连击；保持 Miss 归零语义。
- `LanSessionService.cpp:51` 与 `RecordRepository.cpp:95`：两份 `statsJson` 序列化相同 PlayStats 字段，可统一到一个小型公共编解码工具。
- 网络 `readStats` 先重复计算成功数、权重和 Combo 关系，随后又调用 `ScoreService::isValidStats`。保留网络字段类型/范围检查，把业务统计关系统一交给 ScoreService。
- 多个文件各自实现整数读取和范围检查。仅统一真正相同的部分，保留网络/成绩/谱面各自的限制；不必为少量重复建立复杂模板框架。
- `MainWindow.cpp` 在建房、加入、单人启动和设置处重复检查昵称；用一个小函数统一去空白和长度规则。

效果：这类修改能实质减少重复，同时让“规则在哪里”更清楚。新增公共工具的净行数也应计入，不能只统计原文件减少量。

**C. 清理确定无用的成员和分支。**

- `RecordRepository.h:30` 的 `loaded_` 仅在 load() 被赋值，没有被读取，可移除。
- `RecordRepository.cpp:49` 的 `missingMeansSolo` 参数始终使用默认 false，其旧兼容分支没有实际调用，可删除参数及分支。
- `MainWindow.cpp:839` 的 `enterLan(bool host)`，当前应用和 UI 测试调用全部传 false；实际建房由页面按钮调用 createRoom。可以改为无参并去除未使用的 true 分支。
- `effectVolume` 当前只有模型/设置读写/测试使用，没有实际分级点击音效和界面控件。可选择保留为未来字段，或清理它；若删除需同步调整设置读取规则和测试，避免现有设置突然无法读取。

效果：收益较小，但风险容易控制。不能把 `audio.positionMs`、引擎 `activeHolds()` 等测试正在使用的接口直接认定为无用。

**D. 简化排行榜实现。**

`RecordRepository.cpp:367` 先排序，再找每个昵称最佳，再排序。可按“筛选同榜 → 用 QMap 按昵称保留最佳 → 最终排序 → 生成名次”的直线流程组织。保留同分较早时间优先、最终稳定排序、同分并列和最多20名等现有行为。

**E. 减少目录干扰，统一构建入口。**

只保留一个日常构建入口，检查是否还需要 `tests/core/CMakeLists.txt` 与 `tests/network/CMakeLists.txt` 两个独立入口。它们有独立构建用途，并非天然错误；若统一走根 CMake，则可取消这些旧入口并更新说明。旧 `core-tests*`、`network-tests` 构建目录可以在确认无需历史日志后清理或移出工作区，`build/evidence` 的报告截图应先保留。

可通过 VS Code 排除显示设置隐藏 `build/out`；现有 `.gitignore` 已忽略它们，但忽略 Git 跟踪不会自动隐藏编辑器目录。不要通过删除测试或第三方运行库来追求源码减少。

### 第二优先：保持基本玩法，调整额外复杂度

**F. 处理长按暂停恢复的复杂状态。**

当前暂停会清键态、记住活动长按，恢复时要求重新按住。这涉及 `GameEngine.cpp:215` 后的多个方法、`MainWindow::togglePause/tryResume` 和相关测试。可以选择更直观的规则，比如取消暂停只保留重开；或简化恢复交互，但必须明确长按如何处理。减少了功能或改变了玩法，需要同时改帮助和需求，不能悄悄删状态。

**G. 简化存档模型中的派生结果。**

PlayRecord 同时保存 `stats`、独立 `score`、包含 `score/accuracy/grade/FC/AP` 的 `result`，因此需要大量一致性验证。可以以 stats 与谱面/规则标识为真源，读取后按匹配的规则计算展示结果，或者至少去掉重复的 score。

这会改变存档格式，需要明确旧文件读取/重置策略；并且若以后修改计分公式，必须根据 rulesVersion 使用正确规则，不能把旧成绩用新公式重算。当前已采用“识别的旧版本重置”，并不存在一个庞大的旧数据迁移框架可供直接删除。

**H. 把资源准备期间的重复工作做一次并复用。**

歌曲索引加载会读取各难度谱面；预览、排行、开局又会读取；`resourceConfig()` 每次会计算整份音频哈希。可缓存加载成功的 Chart 和音频哈希，在歌曲/文件变化时失效。它主要减少重复 IO 和错误路径，未必减少代码；不宜为仅两首歌建立复杂缓存系统。

**I. 歌曲生成脚本按需要合并共用部分。**

两个生成脚本有包络、音色合成、WAV 写入、音符和同时键添加、索引更新等共用思路。可以用一个 `songgen_common.py` 加两份曲目定义复用；也可以直接把它们标记为资源制作工具，日常不读。它们共436行，不计入4,386行应用源码；共用脚本会增加一个文件，是否更易懂应优先于追求文件数。

### 第三优先：若允许缩小需求，取消局域网

这是减少应用源码最多的选择，但会改变已确定的“局域网联机版”需求。

可直接去掉 `src/network` 的6个文件、1,263行，约占28.8%；同时精简 MainWindow 的房间页、网络信号、联机结算、设置与成绩中的联机字段，以及对应测试和文档。不能只删 network 文件夹：目前单人倒计时也调用 `lan_.localNowMs()`，要先给主流程提供独立单调时钟。随后才可移除 Qt Network 依赖。

“4,386 - 1,263 = 3,123行”只是扣除网络目录的算术值，**不是可编译精简版的实测行数**。界面和存储还会减少，独立时钟等替代实现又会增加；最终数量需要完成后重新统计。若目标是保留当前全部功能，不建议先走这条路。

## 9. 哪些看似复杂但应保留

- 题目基础：三档难度、单点/长按/连续/同时键、Combo、评级、排行。
- 核心正确性：统一歌曲时间、忽略按键自动重复、单个音符只结算一次、长按尾部规则、延迟帧下的结算次序。
- 文件基础：必要的类型/轨道/时间检查，错误提示，同局不重复保存，QSaveFile 原子写入。
- 保留联机时：TCP 拆包、资源一致性、准备状态、统一开局、超时断线和结果确认。删掉这些只会把复杂度转为难排查的错误。
- `.h/.cpp` 的正常分工、必要模块边界，以及能证明行为未变的测试。

不建议把多个模块合并成一个大 .cpp、把正常循环改成难读的一行表达式、去掉空行注释来压行数。题目还明确要求变量、方法和关键语句说明；当前部分成员注释偏少，删注释与课程要求相反。
