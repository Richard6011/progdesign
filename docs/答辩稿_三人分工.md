**【组长：开场、架构、UI 与玩法】**

各位老师好，我们小组的项目是《音符碰撞》，一个运行在 Windows 上的四轨音乐游戏。我先介绍整体结构、界面和玩法，随后两位同学介绍游戏核心与数据管理，最后由我介绍联机功能并进行演示。

项目支持本地账号登录、歌曲和难度选择、单人演奏、成绩结算、排行榜，以及局域网双人对战。目前有《小星星》和《霓虹脉冲》两首歌曲，每首歌有三档难度。

整体采用模块化设计。页面布局、游戏规则、数据和网络逻辑主要使用 C17，Qt 窗口接口使用 C++17。业务模块编入一个核心静态库，主程序再调用核心库和图形接口。这样界面、判定、资源和网络各有对应模块，查找和修改功能比较方便。

UI 按页面组织，包括登录、主菜单、选曲、演奏、结算和排行榜等。程序用页面枚举记录当前页面，每帧根据页面调用对应绘制函数。按钮、输入框和标题等公共元素封装为函数，减少重复代码。

界面交互的流程是：Qt 收集键盘、鼠标事件，转换成统一的 UiEvent，C 层再处理。绘制按钮时记录按钮区域和动作，点击后通过坐标找到动作，交给主程序执行。图形接口提供画矩形、画线和文字等能力，页面内容由 C 代码决定，并通过离屏图像绘制后统一显示。

玩法上，D、F、J、K 对应四条轨道，音符到达判定线时击打。单点按一次，长按需要保持到尾部，连锁节点需要逐个击打，同时按键分组要求按下对应的多个轨道。三档难度通过音符密度、多键组合和音符接近时间形成差异。

为了让玩家及时理解自己的表现，界面显示轨道高亮、判定等级、连击、分数和准确率，结束后给出评级。单人模式支持暂停和继续，设置中可以调整音乐音量和输入校准偏移。选曲、演奏、结算和排行榜构成完整的游玩流程。

**【成员二：主循环、音乐时间、判定与计分】**

我主要介绍程序的运行流程和游戏引擎。主程序完成初始化后，在循环中依次处理输入、更新网络、推进游戏并绘制界面。当前应用逻辑采用单线程循环，模块通过各自的状态和接口协作。

游戏数据分为谱面数据和本局运行状态。谱面记录音符的轨道、时刻和类型；运行状态记录音符是待判、正在长按，还是已经命中或漏击。每局单独分配运行状态数组，重新开始时不需要修改原始谱面。Chart 管理音符数组，Engine 借用谱面并管理自己的运行数组，退出时分别释放。

音乐游戏首先要保持时间一致。我们的判定以音频模块返回的音乐播放毫秒位置为依据，画面也根据音符目标时刻与当前音乐时刻的差来计算位置。这样帧率变化时，游戏仍然围绕同一条音乐时间线运行。

按键到来时，引擎在对应轨道查找判定窗口内最早的待判音符。输入时刻加上校准偏移，再减去目标时刻，得到时间误差。绝对误差在 90 毫秒以内为 Perfect，150 毫秒以内为 Great，220 毫秒以内为 Good；音符超过可击打窗口仍未命中，就结算为 Miss。程序还会过滤重复按住，避免一次持续按键连续击中多个音符。

计分权重分别是 1000、700、400 和 0，累计后除以整张谱面的最大权重，再换算为百万分。例如四个音符分别得到 Perfect、Great、Good 和 Miss，最终是 525000 分。分数计算使用固定音符总数，连击单独统计，Miss 会清空当前连击。中间乘法使用 64 位整数，避免计算过程中溢出。

长按在命中头部后进入保持状态，记录头部判定，持续到尾部再结算一次；提前松开计 Miss。引擎推进时按照事件实际到期顺序处理漏击和长按尾部，让不同更新步长下的自动结算顺序保持一致。

暂停时音乐和引擎同时冻结，并清空物理按住状态。如果暂停时有活动长按，继续前需要重新按住对应轨道。所有音符完成判定并且音乐接近结束后，程序才进入结算和成绩保存流程。

**【成员三：资源、账号、设置与成绩】**

我主要介绍资源加载和本地数据管理。曲库通过 JSON 索引记录歌曲信息、音频路径和三档谱面路径。谱面中，每个音符包含 ID、轨道、目标时刻、类型等字段，长按还有结束时刻，连锁和同时按键有分组信息。

加载资源时，程序先检查字段类型和范围，再检查音符 ID 是否重复、同轨音符是否与长按冲突，以及分组是否满足要求。之后按时间、轨道和 ID 排序，形成确定的处理顺序。音频还要检查 WAV 格式和时长是否与谱面匹配，避免资源问题影响演奏。

仓库中还提供 Python 资源生成工具，用于生成 WAV 音频和对应谱面。游戏运行时直接读取已经生成的资源。增加歌曲时，需要补充音频、三档谱面和曲库索引。

用户数据保存在本机 AppData 下的 NoteCollisionC 目录，账号、设置、成绩分别保存为 JSON 文件。账号注册时保存盐值和 SHA-256 摘要，登录时重新计算摘要进行比较。密码不会作为明文写入账号文件，也不会通过联机协议交换。

成绩保存要求统计完整，并利用会话标识避免重复记录同一局。排行榜会先按单人或联机模式、谱面 ID、版本、哈希、难度和规则筛选，再按分数排序，同分显示并列名次。这样参与比较的成绩来自相同谱面和规则。

文件保存时，先把新内容写入同目录临时文件，完整写入并刷新后，再替换目标文件，减少直接覆盖原文件时写入中断造成的损坏。读取到损坏或未知版本的成绩文件时，会保留原文件并禁止覆盖。音乐音量和输入校准偏移也可以保存，在下次启动时恢复。

**【组长：联机流程与演示衔接】**

双人模式采用局域网房主和客人的结构。一方创建房间，另一方输入房主的 IPv4 地址和端口加入。网络模块使用 Winsock TCP，通过非阻塞方式在主循环中轮询，连接和收发等待不会一直阻塞界面操作。

TCP 提供的是连续字节流，一次接收可能只有部分消息，也可能包含多条消息。因此我们给每条 JSON 消息加上四字节长度头。接收端先累计数据，只有长度头和消息体齐全后才取出处理，剩余数据继续保留。协议还检查版本、序号和对局标识，约束消息内容及其处理顺序。

连接成功后，双方先握手，再校验资源。房主公布曲目、难度、规则、谱面哈希和音频哈希，客人核对本地资源。双方预加载本地音乐，资源确认一致后才能准备和开始，传输内容主要是配置、统计和控制消息。

共同开局还需要处理两台电脑的时钟差异。客人发送 ping，房主返回自己的时刻，客人根据发送和接收时刻估算时钟偏移，并优先采用往返延迟较小的样本。完成校时和双方准备后，房主安排大约三秒后的开局时刻，客人把它换算为自己的本地时刻，到时分别开始播放本地音乐。

演奏过程中，各自使用本地音乐时间判定，约每一百毫秒交换一次累计统计，在界面上展示对方分数。结束时，双方提交完整统计，由房主汇总结果，客人核对并回复，再完成确认。应用层在结果确认后才保存联机成绩。对局中途退出或连接异常时，未确认的对局会中止。

联机业务用状态枚举区分监听、连接、房间、倒计时、演奏、等待结果、完成和中止。每类消息检查当前状态是否允许处理，减少准备、开局和结算流程混在一起的问题。

| 老师可能问 | 建议回答 |

| 一共有多少函数，平均多长？ | src 共 146 个函数定义，含 Qt 构造及成员函数；平均约 19 行有效代码。口头可说约 150 个、平均约 20 行。 |
| 为什么函数平均很短，却有两百行函数？ | 图形和平台封装有很多小函数，消息分发和动作分发较长；平均数反映整体，不能代表每个函数。后续可按协议消息、业务流程继续拆分。 |
| 项目是否全部用 C？ | 业务和页面布局主要使用 C17，qt_bridge.cpp 使用 C++17 对接 Qt。当前版本不链接 EasyX。 |
| 为什么采用 Qt 接口？ | 用统一 gfx 接口提供窗口、绘图和事件，让 C 业务不直接依赖 Qt 对象，图形层更换时可以保留主体业务。 |
| Qt 是否意味着整个项目跨平台？ | 当前目标是 Windows；音频、网络和平台模块仍使用 Windows API，迁移系统还需要适配这些模块。 |
| 长按算几次分？连锁有额外加分吗？ | 每个长按最终结算一次；连锁逐节点判定，当前复用单点计分规则。 |
| Combo 会让分数翻倍吗？ | 不会。分数按判定权重归一化；连击单独统计，并参与 S 级要求。 |
| S 级、FC、AP 的条件是什么？ | S 要求准确率至少 95%，最大连击达到总音符数的 80%；完整局无 Miss 为 FC，全部 Perfect 为 AP。 |
| 能保证两台机器绝对同时出声吗？ | 校时和计划起播用于减少开局差异；系统调度和音频设备仍有延迟，当前没有持续音频漂移校正。 |
| 联机会传音乐或每一次按键吗？ | 各自使用本地音频与谱面，传输配置、时间相关控制、累计统计及最终结果。 |
| 为什么用 TCP？ | 需要按顺序处理准备、开局和结果确认等消息，TCP 提供可靠有序传输，应用层再处理消息边界和业务状态。 |
| 哈希能防作弊吗？ | 哈希用于比较资源是否一致；统计校验用于检查数值是否自洽。当前没有服务器复核击键的反作弊体系。 |
| 密码是加密保存吗？ | 保存的是加盐 SHA-256 摘要，用于登录时比较；摘要与可解密的加密不同，当前面向本地课设账号。 |
| 如何避免成绩重复保存？ | 应用层记录已保存状态，存储层再按会话标识及联机对局、玩家标识去重。 |
